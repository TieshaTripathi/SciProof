# Optional attestation lifecycle

Scientific verification never calls an EVM provider. Its completed report creates a NOT_REQUESTED audit row. Owner-authorized `POST /runs/{id}/attestation` requires explicit public-association consent and a researcher address. The configured attestor signs; this does not establish ownership of the supplied researcher wallet. No authentication depends on wallets.

DisabledAttestationProvider, LocalDevAttestationProvider and EvmAttestationProvider share a boundary. Disabled is the default. Startup validates enabled chain ID, contract address, private signing key and confirmations. Remote RPC requires HTTPS; local development permits loopback HTTP. Before signing/broadcast/refresh, RPC chain ID, deployed code and contract attestor must match configuration.

Research/version IDs are SHA-256 hashes of their UUID strings; provenance is the original report manifest SHA-256. Artifact summary hashes canonical artifact IDs and SHA-256 values. Score is report confidence scaled to an integer 0–10,000; statuses map VERIFIED=0, VERIFIED_WITH_WARNINGS=1, NEEDS_REVIEW=2, FAILED_VERIFICATION=3, INSUFFICIENT_EVIDENCE=4. Only compact hashes, public address, timestamp and score/status enter the contract.

PENDING means signed bytes are durably saved before broadcasting. The saved transaction hash is computed from the actual signed transaction; it does not mean broadcast succeeded. SUBMITTED requires a successful RPC broadcast or observation of the transaction. Broadcast timeout retains PENDING with BROADCAST_UNCERTAIN; a repeat action resends identical signed bytes. FAILED preparation never invents a hash. A reverted chain transaction is terminal FAILED.

Nonce allocation uses a PostgreSQL transaction advisory lock and the maximum of RPC pending nonce and locally reserved nonce. All SciProof instances using a signer must share this database. Sharing the signer with unrelated software or losing prepared transaction state is unsupported. Pending nonce gaps and funding/fee problems require operator reconciliation; this MVP does not implement fee replacement, remote signing/KMS, automatic finality monitoring or cross-database signer coordination.

Owner `POST /runs/{id}/attestation/refresh` queries actual receipt, canonical block hash, sender/contract, event and stored registry record. CONFIRMED requires `latest height - receipt height + 1 >= BLOCKCHAIN_CONFIRMATIONS_REQUIRED`. Confirmation timestamp comes from the chain block; block number/hash persist only after policy is satisfied. Missing receipt, insufficient depth or changed canonical block removes the current confirmed status. RPC failure downgrades a previous confirmation to SUBMITTED with an unavailable code instead of certifying current finality. An explicit refresh is required to discover subsequent reorganizations.

GET returns last observed audit state; it does not silently contact RPC. `/runs/{id}` overlays current persisted attestation state while the scientific snapshot and provenance remain immutable. Configured confirmation depth is a probabilistic policy, not permanent finality. A trusted correctly deployed registry address is required; this adapter is not a bytecode audit.

Actual local Anvil validation covers deployment, random funded signer, real signed transaction/receipt, three-confirmation enforcement, depth rollback, receipt removal, and rebroadcast of identical signed bytes. This is local EVM validation, not a production-chain transaction. See `blockchain-validation-result.json` and the phase ledger. API usage follows the [web3.py transaction documentation](https://web3py.readthedocs.io/en/stable/transactions.html) and [receipt/block APIs](https://web3py.readthedocs.io/en/stable/web3.eth.html).
